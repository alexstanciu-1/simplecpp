# Template-free accounting application boundary
Doc Status: planning

Status: approved; goal active. The [source-handle slice](results/prelower_source_handles_2026_10_19/README.md) passes accounting and focused O0 proofs. Literal/scalar interfaces and template-free include closure remain in progress.

## Target and audit

For the prepared accounting application, remove templates from the application's
transitive C++ input, retaining original runtime implementations in compiled
middleware. Reuse the existing AST, prepared semantic facts, registry, physical
bindings, specialization engine and layout cache. Prepare only demanded types and
operations. This does not replace the runtime or introduce a C backend.

The [closure audit](results/prelower_template_closure_2026_10_19/README.md)
finds 44 source-class shared specializations and 3,826 template-bearing preprocessed
lines per application unit after the two measured header fixes. Native scalar
headers and source-class ownership remain exposed. Template declarations are in
transitive runtime/toolchain headers, not generated template class declarations.

## Why include removal alone is insufficient

`CPP_Types::has_template_recipe` deliberately excludes source definitions; concrete
selection sees the semantic core before implicit shared storage is applied.
Consequently `Invoice` remains `shared_p<record_Invoice>`. Existing concrete lifecycle
storage can hide the native handle, but it does not yet expose the typed `operator->`
interface needed by ordinary source-field/method emission. Ordinary source construction
still emits the runtime shared/unique allocation template in the application.

`string_t` is a plain native class in `cpp_types`, even though its definition contains
`std::string` and includes UTF templates. A native-template spelling flag therefore
cannot express all implementation exposure. Its literal interface also differs from
the integer-only constructor/native-value interface currently generated by
`CPP_Opaque_Representation`. These are physical contracts, not new semantic types or
new source capabilities.

`bool_t` includes `detail.hpp` despite its scalar representation. Common headers,
standard-library helpers in emitted expressions, exception entry handling and the
runtime PCH must be audited independently of container substitution.

## Proposed bounded implementation sequence

1. Extend existing runtime C++ bindings to distinguish native implementation exposure
   from whether the public native spelling uses template arguments. Template recipes
   continue selecting concrete storage; non-template classes can explicitly request
   the same boundary. Keep this inside existing `cpp_types` ingestion and bindings,
   with validation and configuration invalidation; do not create another registry.
2. Describe the needed physical interfaces using validated binding contracts:
   byte-literal construction and pointer-like payload access first, then scalar
   extraction/construction where demanded. Preserve existing semantic literal kinds
   and source construction decisions. Do not embed arbitrary C++ snippets in metadata
   or dispatch on names such as string/shared/vector in the engine.
3. Select the full stored representation, including implicit shared storage, through
   existing type mapping. Generate concrete lifecycle and typed payload-access
   declarations using the existing representation/member owners. Forward checked
   dereference and allocation to the native runtime. Preserve one payload definition;
   its methods remain under the existing source-declaration/body owners.
4. Reuse prepared object construction and runtime-operation transport for factories
   returning the selected concrete owner. Keep argument sequencing in existing call
   emission. No extra payload allocation, handle copy or proxy object is permitted
   merely to cross the boundary.
5. Give concrete native strings byte-aware literal construction through the same
   physical interface mechanism. Cover embedded NUL, empty/short/long strings, copy,
   move and destruction; keep the runtime's string/storage behavior unchanged.
6. Narrow primitive includes where their declarations genuinely require no templates.
   Move remaining implementation-only helper/exception dependencies behind compiled
   boundaries. Audit application input with PCH disabled; use the existing no-PCH
   build configuration for the template-free acceptance run. A future application
   PCH must contain only the concrete interface closure, not the broad runtime PCH.

These changes cross runtime metadata ingestion, physical binding/rendering, source
construction/member access, and generated-header/layout dependencies. Keep each
vertical proof bounded. Do not silently broaden layout scheduling: recursive source
handles must separate forward payload declarations from complete implementation
requirements. If the existing dependency owner cannot represent that distinction,
report the specific cycle and review its local repair before changing the engine.

## Intended application shape (illustrative names)

```cpp
struct record_Invoice;
class Shared_Invoice {
    // Inline storage sized/aligned by the existing native-layout probe.
public:
    Shared_Invoice();
    Shared_Invoice(const Shared_Invoice&);
    Shared_Invoice(Shared_Invoice&&);
    ~Shared_Invoice();
    record_Invoice* operator->() const;
};

struct record_Invoice {
    Concrete_String label;
    Concrete_Vector_Int amounts;
};

// App: ordinary fields/methods, with substituted physical types.
auto invoice = make_invoice();
invoice->amounts.append(amount);
```

The middleware owns construction/destruction of the original runtime handle in the
inline storage and delegates `operator->` to that original handle. It does not
reimplement reference counting or allocate a second control block. Factory/literal
names and signatures come from existing demand and prepared bindings.

## Validation and risks

- Direct/concrete counter parity for shared identity, copies, moves, destruction,
  exceptions and nested references; verify pointee identity and allocation counts.
- Recursive class declarations, source-defined template arguments and source method
  access must compile without losing complete-type requirements or creating layout
  cycles. Alternative runtime bindings must work without engine edits.
- Byte-exact literals/output and evaluation order; no extra string allocations or
  copies. The existing integer mechanism should become a consumer of the generalized
  physical interface instead of a parallel implementation.
- Incremental removal/replay, configuration switching, body-only edits and layout
  invalidation. Do not infer cache correctness merely from clean builds.
- Accounting passes all 998 checks with no silent template fallback. Preprocess every
  app unit without PCH, inspect its dependency closure and confirm no remaining
  template declarations/uses. Clang traces provide independent instantiation evidence.
- Only after correctness, compare O0 sequential and parallel app wall times with
  middleware/layout/PCH costs reported separately. O2 remains deferred.

The principal risks are wrong stored-vs-payload selection, extra lifetime operations,
recursive header/layout dependencies and hidden template imports. This is a physical
interface extension, not an include-name cleanup. No performance ratio is promised.
