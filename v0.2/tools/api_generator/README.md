# Public runtime API generator

Doc Status: supporting

Runtime public APIs follow the [minimal public header rule](../../specs/runtime_public_headers.md).

The production generator runs on **64-bit PHP 8.5 or later**, with no Composer
packages. It reads runtime metadata, publication requests and native C++ target
facts; prepares the requested API; then renders C++ headers, definitions,
`prepared.json` and `inventory.json`. It does not parse compiler source code.

The PHP implementation replaces the Rust API tooling. It preserves the public
behavior and generated bytes, without reproducing Rust's structs, enums or ownership
mechanics. Prepared records are PHP arrays. Object-valued JSON maps use `stdClass`
to preserve the distinction between empty objects and lists. The prepared description
is also the rendering input, avoiding a second serialization model.

## Owners

- `generate.php`: command dispatch, input reads, publication and freshness checks.
- `php/input.php`: small JSON reader and metadata validation helpers. JSON strings
  use PHP's decoder; container/number handling preserves decoded duplicate-key
  rejection, number spellings, object/list distinctions and a 128-container limit.
  Semantic integer fields require exact nonnegative PHP integers; no supported
  field requires values beyond the signed 64-bit host range.
- `php/target.php`: explicit C++ target facts/context validation.
- `php/submodules.php`: shared provider/dependency planning, compiler binding resolution
  and assembly of movable string/output declaration groups. Runtime group providers
  are independent of compiler strategies; other families keep existing renderers.
- `php/scalars.php`: integer, boolean, null and floating API preparation.
- `php/families.php`: strings, vectors, carriers, hashes, datetime and record ownership.
- `php/boxed.php`: optional mixed/dynamic publication with measured inline layouts,
  explicit scalar factories and same-family container operations.
- `php/compiler_families.php`: explicit family expansion and promotion-permission finalization.
- `php/compiler_plans.php`: type/representation, binding, safety and concrete operation validation/planning.
- `php/render_compiler.php`: compiler-generation entry point, planning orchestration and PHP emission;
  loads both planning files so callers keep the same entry point.
- Other `php/render*.php`: runtime rendering from prepared facts.
- `templates/*.cpp.tpl`: readable C++ fragments with named `@placeholder@` slots.
  These retain the existing output spelling; no Rust source is a build input.

Runtime semantics remain in `runtime/src/` and the family contracts in `specs/`.
Native layouts come from `tools/layout_probe/`, not PHP's host object layout.
External record traits remain C++ compilation obligations.

## Commands

From `v0.2/`, configure/build with Clang, libc++, Ninja, mold, PHP and Python:

```sh
cmake --preset default
cmake --build --preset default
ctest --preset default
```

CMake selects `PHP_EXECUTABLE` (a 64-bit PHP 8.5+ binary found on PATH) and creates two launchers in the build directory.
The positional runtime launcher supplies that build's explicit native facts:

```sh
./build/clang/scpp_api_generator runtime/metadata/runtime.json \
  build/clang/runtime-publication.json runtime/generated --check
```

The general launcher accepts the same commands as `php tools/api_generator/generate.php`:

```text
emit-compiler METADATA FACTS CONTEXT OUTPUT [--check]
emit-runtime METADATA PUBLICATION FACTS CONTEXT OUTPUT [--check]
emit-scalars METADATA PUBLICATION FACTS CONTEXT OUTPUT [--check]
prepare-runtime METADATA PUBLICATION FACTS CONTEXT
prepare-scalars METADATA PUBLICATION FACTS CONTEXT
prepare-integer-construction METADATA PUBLICATION FACTS CONTEXT
validate-target FACTS CONTEXT
```

Preparation commands print JSON. Successful generation/check prints JSON containing
`status` and `artifacts`. Failures exit 1 with stderr and no success output.
Scalar projections reject non-scalar demands; complete runtime preparation validates
registered optional-family metadata even when that family is not requested.

Complete preparation/rendering precedes cleanup and writes. The output root is
dedicated generated storage. Normal generation fully clears `.hpp`, `.cpp` and
`.json` files recursively, then emits the complete new publication. Other extensions
are preserved; symlink directories are not followed. The versioned `inventory.json`
manifest (`generator`, `version`, `files`) is written last. Bump `OUTPUT_VERSION` in
`php/publication.php` when the output contract changes; old/malformed manifests need
no migration because regeneration always starts with cleanup.
`--check` is read-only and rejects missing, changed or obsolete generated files.
Publication is per-file, not transactional.
Do not run concurrent writers against one output directory.

## Rebuilds and proofs

Every CMake build checks native target context; unchanged probe files keep their
timestamps. Changes to PHP sources, C++ templates, metadata, publication or native
facts invalidate generation. An unchanged build does not regenerate or recompile.
`BUILD_TESTING=OFF` still runs the production probe and generator.

The frozen fixtures are independent regression references, never production inputs:
130 accepted runtime cases and 19 scalar cases require exact generated bytes;
247 runtime and 537 scalar cases require rejection. The scalar suite also compiles
the 2,692-signature matrix. CTest covers publication/freshness, native probe
invalidation, public header boundaries and compiled runtime consumers. PHP tests
cover lexical numbers, Unicode, duplicate keys, depth, target validation and
hash/datetime/layout contracts formerly covered by Rust unit tests.

```sh
cmake --preset ubsan
cmake --build --preset ubsan
ctest --preset ubsan
python3 -B tests/build_cutover.py
```

The source-only proof removes the compiler from a temporary export and verifies that no Rust source
or toolchain configuration is present, then builds/tests the runtime, checks PHP/template invalidation,
and exercises production builds with datetime enabled and disabled.

The compiler is now PHP: `compiler/my-try/` is being mined incrementally into
`v0.2/compiler/`. Rust sources and toolchain configuration have been removed.

## Core and numeric demand

Core's default integer/byte types are int64 and distinct byte; float64 remains core.
Additional integer widths require `"modules": ["numeric"]` in publication metadata.
Only explicitly requested types/operators are emitted. The build option
`SCPP_ENABLE_NUMERIC=ON` composes `runtime/metadata/numeric_publication.json` with
core. This is API publication selection, not implemented source-level PRJ parsing.
See [the numeric/byte and cleanup contract](../../specs/numeric_module.md).

## Optional native bridge

CMake defaults `SCPP_ENABLE_NATIVE_BRIDGE=OFF`. Enable it to publish native C++
scalar operator adapters, then explicitly include `<scpp/native_bridge.hpp>`.
The build selects its request in `build/clang/runtime-publication.json`.
Direct generator callers opt in by supplying `headers.native_bridge` and native
operator requests; omitting the header requires omitting those requests as well.
Explicit native constructors are available independently. See the
[integer contract](../../specs/integer_slice.md#optional-native-operator-publication).

## Compiler backend publication

Ordinary comparisons and strict identity share `compilerComparisonStrategy` for
native/string execution, operator spelling, storage and bool-result bindings.
Their admission remains independent: strict identity requests value equality from
the resolver directly, without constructing synthetic ordinary-comparison metadata.
Each policy supplies its own binding; both require the runtime string operations
that their emitted code uses. Removing either policy does not disable the other.

Compiler generation separates validation/planning from per-type emission. Output, update,
unary and promotion plans are built once; their renderers consume only the rows
indexed under the current canonical type (the left operand for promotions).
Promotion plans retain validated operand conversions and compound write-back
strategies. These are temporary generator arrays, not compiler runtime tables;
the emitted methods remain direct specialized PHP code.

`compilerFamilyPlan` owns the expansion sequence on a private metadata copy:
conversion families → mixed numeric operations → integer operations → three-way
operations → promotion-permission finalization. Expansion functions do not invoke
other families. The finalizer indexes conversion rows by source/destination and
consumes temporary requirements emitted by the owning policies, preserving order.
Family-generated conversions derive permissions from admitted promotions; integer
and three-way family policies also authorize their own required conversions, as
before, even when those conversion rows were explicit. Explicit promotion rows
alone cannot authorize themselves on explicit conversions. Missing/invalid
conversions remain errors; typed-destination, explicit-cast and compound-write-back
contexts remain independent. No metadata schema or generated interface changes.

Validation for this separation compared all generated bytes across 48 successful
metadata fixture renderings before/after, alongside existing rejection tests.
When metadata contains several independent errors, validation phase ordering may
change which error is reported first; individual rejection messages are retained.

`emit-compiler` generates PHP int64/null/bool/byte/float64/string definitions and source-name/literal
registration from runtime metadata and validated native facts. `compiler.modules`
declares always-available default-runtime membership; `compiler.integer_literals`
records decimal/reject/signed-carrier policy. `compiler.value_types` describes core
literal/representation mappings; `compiler.conversions` supplies generated conversion
branches. Byte width/storage metadata is shared with runtime generation. Typed
destinations authorize checked conversion; explicit source cast syntax, operators,
overloads and further types remain deferred. `compiler.floating_literals` owns
rounding/overflow/underflow admission; normalized target facts retain validated
binary64 precision/exponent information for generated float preparation/lowering. See [the type contract](../../compiler/docs/types.md).

Output lives in `compiler/generated/`, independently of runtime API demands; compiler
inventory version 6 lists the new definitions. Cleanup remains limited to `.php` and
`.json`. CMake checks and repairs publication while preserving unchanged timestamps.
Runtime publication bytes and cleanup are unchanged. The parity baseline update for
this slice changes input hashes only; all artifact hashes, prepared models, rejection
outcomes and native facts were compared and remained identical.

Publication manifest version 2 records the native string byte-count API change.
String constructor counts and size results use the prepared native representation;
the wrapped count signature is no longer emitted. See [string boundaries](../../specs/string_slice.md).

## String/output submodule verification

The core string/output providers and their direct public dependencies live in
`runtime/metadata/runtime.json`. Compiler bindings refer to runtime declaration
groups for helpers and semantic `type_export` identities for types; names and
public paths are resolved once during compiler generation. Runtime
publication version 3 also records `private/output_provider.hpp` for the compiled
output implementation. Default APIs and scalar storage remain unchanged.

Run the relocation, native include-selection, incremental recovery and publication
proof after building `scpp_runtime`:

```sh
XDEBUG_MODE=off python3 -B tools/api_generator/tests/submodules.py \
  --output build/submodules-proof
```

The proof uses isolated publications and compiler bootstraps, never replaces the
production generated PHP, and writes stage timings/include closures to
`results.json`. It is registered as CTest `runtime_submodule_providers`.

The shared plan separates provider nodes from declaration groups. Group contracts
supply intrinsic dependencies and exported binding roles; the planner validates
dependency reachability, and compiler resolution rejects wrong owners or migrated
literal-header fallbacks. The provider proof also regenerates handlers and restarts
the real project compiler against an existing application/native build. Restart
retained PHP compiler processes after regeneration; hot replacement is not supported.


The export plan resolves `requires_exports` into ordinary provider edges before
cycle and reachability checks. Runtime export names reuse canonical declarations
and existing aliases; the scalar adapter checks real renderer placement. Include
selection never inspects representation or conversion strategy. Tests cover a
`uint8` export spelled `byte`, string type relocation, invalid export identities and
placement, all-flavor recovery, and restarted cached application/native rebuilds.

Scalar publication paths must agree with metadata provider paths; the adapter rejects
conflicts before publishing. String cast dependencies come from the actual publication,
not the enabled conversion-policy catalog. The provider proof covers both rules and
an independent spelling-only cached rebuild using an executed checked byte conversion.
