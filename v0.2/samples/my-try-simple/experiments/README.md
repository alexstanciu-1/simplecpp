# Regex tokenizer experiment
Doc Status: supporting

This standalone PHP-flavor prototype is not integrated into the compiler.
Run from the repository root:

```sh
XDEBUG_MODE=off php v0.2/samples/my-try-simple/experiments/tokenize-regex.php
```

Measured locally on WSL, 2026-11-02, PHP 8.5.7, PCRE JIT enabled. Fifteen
warm runs with rotating method order. File reading, source snapshot construction,
pattern construction and equivalence checks are outside timing. Timed operations
include matching/scanning, classification, token allocation, token-list validation,
and result release. The current tokenizer constructs punctuation buckets per file;
the regex prototype builds its patterns and punctuation map once per process.
Thus this compares complete candidate paths, not only matching algorithms.

`preg_match_all` collects whole lexemes with byte offsets, using a noncapturing
outer group. `preg_split` uses the same lexical alternation as captured delimiters,
retaining offsets; it is not whitespace splitting. Both include trivia in the match
results and discard it when constructing tokens. Both allocate intermediate PHP
arrays and strings that the current direct scanner does not need.

Every token kind, byte offset and length matches the current tokenizer for all
257 sample files, a synthetic 64 KiB integer/echo file, and a lexical fixture with
comments, escaped strings, multiline strings, decimals/exponents and punctuation.
The 64 KiB input is generated by this harness, not the panel's exact saved example.

This is valid-input corpus equivalence only. The prototype does not implement all
invalid-input checks/diagnostics: numeric suffix rejection, malformed strings or
comments, invalid split leftovers, and diagnostic positions need production work.
CPP/JS flavor rules, adversarial PCRE limits and broad lexical regression testing
are also outside this experiment. Do not use the prototype as a compiler lexer.

## Results

Times below are median [min–max] milliseconds. Raw samples are retained alongside
this report in `tokenize-regex-results.json`.

| Corpus | Current | preg_match_all | preg_split |
| --- | ---: | ---: | ---: |
| my_try_simple | 21.50 [21.25–22.45] | 4.19 [4.11–5.22] | 4.07 [4.00–4.60] |
| integer_echo_64k | 30.49 [29.91–33.39] | 12.69 [12.10–13.59] | 12.52 [11.77–13.79] |
| lexical_fixtures | 0.16 [0.15–0.23] | 0.05 [0.05–0.08] | 0.05 [0.05–0.06] |

The 257-file corpus contains 42,195 bytes and 4,870 tokens; its path comments are
relatively long. The synthetic echo corpus contains 65,598 bytes and 14,616 tokens.
The latter allocates far more token/match records per input byte, so the small-file
speedup must not be extrapolated to all source. Memory and malformed-input behavior
have not been benchmarked. These results justify considering a bulk PCRE scanner
for PHP; they do not establish a universally faster replacement or a native design.

## UTF-8 preg_match_all experiment

The harness now also runs `match_all_utf8` with the PCRE `/u` modifier. It uses
exactly the same lexical alternatives and explicitly ASCII identifier/whitespace
classes. This enables UTF-8 validation and code-point matching inside strings and
comments, without introducing Unicode identifiers, Unicode whitespace, normalization
or a BOM policy. `PREG_OFFSET_CAPTURE` offsets and `strlen` token lengths remain
byte-based, preserving the compiler token representation.

All tokens match the byte scanner on the original corpora and a new roughly 64 KiB
Unicode corpus (Romanian, Greek, Arabic, Japanese/Chinese, emoji and combining
marks in strings/comments, including an escaped multibyte character). Assertions
also verify that non-ASCII identifiers and non-ASCII whitespace remain rejected.

Eighteen malformed-encoding cases are rejected with `PREG_BAD_UTF8_ERROR`: isolated
continuation bytes, overlong encodings, truncated sequences, surrogate encodings,
code points above U+10FFFF and invalid lead bytes, each in a string, line comment
and block comment. No partial token list is returned on a PCRE failure.

This is a deliberate experimental difference from the current byte scanner, which
permits arbitrary interior bytes in strings/comments. Adopting UTF-8 validation
would require deciding the source-encoding contract; no production behavior has
changed. Existing prototype limitations for other malformed lexical input remain.
PCRE failure reporting currently has no precise invalid-byte diagnostic location.

Latest same-run comparison, 15 warm samples; median [min–max] ms. Raw results:
[tokenize-utf8-results.json](tokenize-utf8-results.json). The earlier byte-only
measurement is preserved separately.

| Corpus | Current scanner | preg_match_all bytes | preg_match_all UTF-8 |
| --- | ---: | ---: | ---: |
| my_try_simple | 22.170 [21.742–25.580] | 4.103 [3.993–4.223] | 4.105 [4.012–4.490] |
| integer_echo_64k | 30.246 [29.644–35.472] | 12.382 [11.680–13.283] | 12.352 [11.722–15.263] |
| lexical_fixtures | 0.155 [0.154–0.192] | 0.049 [0.048–0.056] | 0.048 [0.047–0.050] |
| utf8_text_64k | 15.284 [14.994–16.795] | 4.487 [4.048–6.629] | 4.270 [3.889–5.989] |

UTF-8 mode has no meaningful observed overhead on these inputs. Small apparent
speed differences are within run variation, not evidence that UTF-8 is faster.
