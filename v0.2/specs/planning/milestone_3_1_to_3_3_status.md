# What remains in milestones 3.1–3.3

Doc Status: planning

Audit of committed v0.2 PHP compiler work through `985dd2d23`, 2026-11-19. The reference points are the [bootstrap milestones](v03_bootstrap_implementation_plan.md#3-object-relationships--a-small-ast-family), the [language contract](../../../specs/inheritance_v0_2.md), compiler admission and committed executable proofs. This review checked committed source, tests and the implementation plan. Test links identify executable evidence; this documentation pass did not rerun the suites.

## Verdict

| Group | Bootstrap acceptance criterion | Status |
| --- | --- | --- |
| 3.1 | One base, derived storage, inherited access, protected access and construction | Covered for the supported class and struct models. |
| 3.2 | Class presence contracts, shared base views preserving identity and destruction, virtual/abstract methods and overrides | Covered for classes with the agreed relaxed instance-property policy and exact callable signatures. |
| 3.3 | Subtype and interface-capability tests, with an explicit checked narrowing operation | Covered for shared classes and interfaces. Exact concrete-type identity has been inventoried separately. |

The [AST-family proof](../../compiler/tests/ast_parent_lifetime_native.py) combines a base-typed operation, concrete nodes, virtual behavior, capability access and weak parent links. Passing this proof demonstrates the design on a small tree. Translating the production parser and retaining a real edited tree are later bootstrap checks.

## 3.1 — Base storage, construction and inherited access

Implemented: one inline base subobject, inherited field lookup, distinct private/private fields, protected receiver checks, inherited constructor contracts/defaults, explicit and implicit base initialization, access checks and base-before-child initialization. Static data resolves to its declaring owner. Explicit type, lexical self and ancestor access work. Expression-qualified and late-static data support reads, plain writes, discarded compounds and prefix/postfix updates. Constants support reads. [Layout and collision checks](../../compiler/types/struct.php) · [Constructor and inheritance suite](../../compiler/tests/extends_native.py) · [Static data tests](../../compiler/tests/protected_static_data_native.py)

| Remaining area | Scope and decision |
| --- | --- |
| Compound and increment/decrement updates with the newer static qualifiers | Discarded compounds and prefix/postfix updates are implemented for late-static and expression-qualified properties. Expression qualifiers evaluate once before the update. Value-producing updates and indexed mutation remain open. [Preparation](../../compiler/04_analyze/prepare/prepare.php) · [Property update contract](../../../specs/static_members_v0_2.md#property-updates--2026-10-07) |
| Additional construction surfaces | Derived keyed `data` construction, base-first synthesized inputs and constructor `set:` are broader initialization contracts. The completed proof covers ordinary inline/shared construction and base constructor binding. Reference/variadic constructors are separate callable work. Abstract constructors remain explicitly excluded. Coordinate broader initialization work with its owner. [Construction contract](../../../specs/inheritance_v0_2.md#construction-copying-and-cleanup) |
| Authored destructor behavior in a hierarchy | Native subobject cleanup and concrete destruction through shared base views have evidence. Source-authored destructor bodies, visibility and lifecycle rules require the destructor feature and its own proof. The bootstrap audit found no production source-authored destructor requirement. [Inheritance support](../../compiler/docs/inheritance.md) · [Language audit](v03_bootstrap_language_audit.md) |

Keep single record-base inheritance, existing collision diagnostics and current protected receiver rules. Multiple interface capabilities are a separate relationship. Static storage for nullable object handles and lazy type singletons belongs to **5.2**, even when the factory allocating the object uses `new static()`. [Implementation order](v03_bootstrap_implementation_plan.md#3-object-relationships--a-small-ast-family)

## 3.2 — Behavior through base views

Implemented: required/optional class function boundaries, shared derived-to-base class conversions, concrete destruction and allocation identity through adjusted views, ordinary/virtual/abstract/final methods, mandatory override intent and explicit ancestor calls. Static calls distinguish lexical and called types. Self/parent forwarding, explicit-type reset, descendant static redeclaration, late-selected data/methods and shared factories have landed. The earlier plan entry listing late-static lookup and shared factories as future work is historical. Inherited public final methods also satisfy interfaces introduced on descendants, including when the inherited implementation is final virtual. [Final-interface proof](../../compiler/tests/interfaces_native.py) · [Class contracts](../../compiler/docs/classes.md) · [Shared upcasts](../../compiler/tests/shared_upcasts_native.py) · [Dispatch and factories](../../compiler/tests/called_methods_native.py)

| Remaining area | Scope and implementation consequence |
| --- | --- |
| Shared-value callable variance | Current override/interface checks require exact types. The spec allows a broader by-value shared parameter and a narrower by-value shared return. This needs directional signature checking and dispatch adaptation. Defaults remain selected from the caller's contract. Static redeclarations and references retain exact contracts. [Signature check](../../compiler/04_analyze/prepare/methods.php#L103) · [Variance contract](../../../specs/inheritance_v0_2.md#shared-value-callable-variance) |
| Struct polymorphism and shared struct views | Explicitly shared structs exist. Shared derived-struct to base-struct conversion, abstract structs and polymorphic struct contracts have broader spec coverage than the active class-oriented implementation. Separate owner-preserving upcasts from abstract-value admission and virtual dispatch. Inline derived-to-base slicing stays excluded. [Shared conversion](../../compiler/types/struct.php#L551) · [Abstract declaration checks](../../compiler/04_analyze/prepare/methods.php) |
| Additional callable shapes | Reference-return virtual/interface calls and broader callable forms such as variadic forwarding require callable support, lifetime/origin checks and separate executable proofs. Exact writable reference parameters already supported by the binder are a different capability. [Virtual method contract in the compiler](../../compiler/docs/virtual_methods.md) |
| Presence and owning the current instance | Keep relaxed instance fields as agreed. Required class locals currently need an initializer. Definite assignment and obtaining an owning class `this` value are separate work; field/method access through `this` already works. [Class boundaries](../../compiler/docs/classes.md) · [Preparation](../../compiler/04_analyze/prepare/prepare.php) |
| Other ownership families | Exact weak observation and locking work for covered owners. Weak derived/base view conversions and unique derived/base transfers have their own contracts. Borrowing, stored references and cross-thread ownership require separate lifetime decisions. None is needed to dispatch through a shared base class. [Ownership contracts](../../../specs/inheritance_v0_2.md#weak-derivedbase-upcasts) |
| Broader called-type propagation | Called-type instances currently belong to static bodies. Carrying a runtime called type through an ordinary instance method, or selecting a static implementation through an interface-typed qualifier, needs a separate design. Shared factories in static bodies are implemented. [Called-type ownership](../../compiler/docs/protected_static_methods.md) |

## 3.3 — Type tests and narrowing

Implemented: same-type/upward tests, checked class downcasts, class/interface capability checks and interface cross-casts where overlap is possible. Empty handles test false; a checked cast on absence or mismatch raises `invalid_object_cast`. Preparation rejects impossible final-class/interface pairs and narrowing from a nonpolymorphic source. The tests exercise required/optional handles, single evaluation, alias identity, adjusted views and incremental ancestry edits. [Admission](../../compiler/04_analyze/prepare/object_access.php) · [Class tests](../../compiler/tests/object_access_native.py) · [Interface tests](../../compiler/tests/interface_access_native.py)

| Remaining area | Scope and decision |
| --- | --- |
| Checked access for explicitly shared structs | The language contract includes shared struct operands and struct targets; current admission explicitly excludes both. First prove same-type/upward views alongside shared struct upcasts. Downcasts require an established polymorphic source. Struct-to-interface cases also depend on admitting struct implementers. |
| Automatic flow narrowing and repeated-check elimination | Today a successful `instanceof` is a boolean fact at execution; source uses `object_cast` to obtain a typed handle. Branch-local smart casts would change source behavior. Eliminating a redundant check while keeping the explicit cast is a separate optimization requiring validity across calls, writes and aliases. Neither is required for the current proof. |
| Exact concrete-type identity | Subtype membership, allocation identity and exact concrete type answer different questions. The inventory found a duplicate-category invariant and compiler-internal type-dispatch uses. A public exact-type operator, reflection API or per-object tag has no agreed bootstrap requirement. Revisit at the real translation use. [Exact-type inventory](class_contract_completion.md#exact-type-inventory) |

Dynamic target names, implicit downcasts, bare-null operands, and checked casts directly on weak/unique owners are outside the bounded object-access contract. Interface inheritance/diamonds and struct interface implementations belong primarily to **3.4**; non-owning generation links to **3.5**; traits and staged attachment to **3.6**. These affect future coverage without reopening the existing class/interface cast proof.

## Proposed order for goal planning

The bootstrap proof can be signed off today under its agreed boundaries. The following are **language-coverage extensions**. If the immediate objective is translating the real AST, proceed to the translation proof and reopen these only for a real source use. If the objective is to broaden 3.1–3.3 together, the most coherent first goal is **explicitly shared struct views and checked access** (G1–G2). It closes a gap across two groups with one conversion owner and one access owner.

| Order | Deliverable and dependency | Acceptance boundary |
| --- | --- | --- |
| G1 · 3.2 | Enable owner-preserving upcasts from explicitly shared derived structs to shared base structs. Start in [shared handle conversion](../../compiler/types/struct.php) and reuse the class path. | Check assignment, by-value argument and return, empty handles, identity, mutation through the base and final release. Exercise an individual typed element and a conditional join where admitted by the common conversion path. Reject inline slicing, whole-container widening and reference rebinding. |
| G2 · 3.3 | After G1, admit same-type and upward tests/casts for shared structs in [object-access preparation](../../compiler/04_analyze/prepare/object_access.php). | A present upcast keeps identity, an empty operand tests false and a checked cast on it fails. Evaluate the operand once. Reject unrelated structs and downcasts from a nonpolymorphic source. No per-object tag is needed for upward access. |
| G3 · 3.2 → 3.3 | Separate goal for virtual/abstract structs, then checked downcasts through a polymorphic shared struct base. Depends on G1–G2 and an agreed inline-value boundary. | Prove abstract construction rejection and dispatch through a shared base, plus successful, mismatched and absent downcasts. Before broadening struct eligibility, check concrete inline copy/layout, container eligibility and destruction. Struct implementers of user interfaces cross into 3.4. |
| G4 · 3.2 | Independent goal for [shared-value callable variance](../../../specs/inheritance_v0_2.md#shared-value-callable-variance). Begin with a native bridge proof for the already-supported class family; extend to struct views after G1 and the relevant dispatch support. | Broader by-value parameter and narrower result preserve identity, absence and caller-selected defaults. Check reverse-direction rejection, exact references, static invariance, final and inherited interface implementations. Keep one authored method body. Signature edits must invalidate the bridge and its callers. |
| G5 · 3.1 | Separate property-expression goal only if value-producing updates are wanted next. First settle the expression-level evaluation contract across ordinary, late-static and expression-qualified properties. | Prefix/compound return the new value, postfix returns the old value; single evaluation, original declaring storage and checked failure before write-back. Indexed mutation of a static collection is a distinct writable-target extension. |

**Common completion gate for a goal.** Run cpp/php/js executable fixtures; edit the base edge, remove a declaration, retry without edits and restore it. Compare emitted artifacts or diagnostics with fresh compilation at each checkpoint. Include an unaffected sibling and verify reuse. For ownership changes, exercise last release and leak checks. Record PHP preparation work and native wall, frontend, LLVM and link timings. Start with existing ancestry watches and occurrence facts. Require a demonstrated need before adding a new retained index or a whole-project pass.

**Decision points.** G1–G2 have a written semantic contract and can be planned together now. Pause if the native representation requires changing shared ownership for every record. For G3, agree the inline polymorphic struct boundary first. For G4, prove the native signature adapter before changing admission; stop if correct dispatch requires replacing the callable ABI broadly. G5 has a separate grammar and evaluation footprint.

**Other work stays with its owner.** Derived keyed construction and constructor binding belong with initialization; source destructors with lifecycle; reference returns, variadics and definite assignment with their respective callable/flow work. Weak/unique conversions and obtaining ownership of class `this` need their respective ownership contracts. Keep the existing required-field policy, single concrete base and nonvirtual hiding rejection. Interface-qualified static dispatch, runtime-called-type propagation through instance methods, smart casts and a public exact-type query need separate decisions. Interface inheritance/diamonds (3.4), generation links (3.5), composition (3.6) and static singleton storage (5.2) have separate milestone owners.
