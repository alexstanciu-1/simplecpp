# Tokenizer avoidable native work

Doc Status: supporting

A C implementation with the same lifetime contract is the reference model. The result must keep the source bytes alive after edits, store each accepted token’s kind and byte range, and expose no partial tokens after an error. A native implementation can retain one source buffer, read it through a stable pointer and length, and fill one presized token buffer. The measured baseline uses handwritten C++. No C timing is available.

| Where | Extra native work observed | When it can be avoided | Evidence and owner |
|---|---|---|---|
| Publishing the token vector on success | The copy path allocates another buffer and copies all completed token records. On the mixed fixture, 5,120 records occupy 122,880 bytes. Publication also allocates a 24-byte storage object. | The local vector reaches its last use and has no observable alias. Transferring it to the result preserves the existing error path. | With the split view, move and direct construction each saved 122,904 requested bytes and two allocations. Both improved median mixed throughput by about 13%. The compiler now emits the transfer for the scanner. With ordinary checked byte reads, all six dev002 builds went from 8 allocations to 6 under the same reserve hint. [Preparation cost and verification](../../v03_bootstrap_implementation_plan.md#25-first-integration-slice--last-use-transfer-of-owned-values). [Matched publication benchmark](byte_access/publication.md). |
| Retaining the source snapshot | The by-value input already has its own bytes. Assigning it to the result copies the source again. For 20,480 mixed-input bytes, the second copy requests 20,481 bytes plus a 32-byte storage object. | The scan can transfer its private input into the result before recognition and read from that stable result owner. The caller and previous results must keep their original bytes. | On the pinned cpp-flavor operator benchmark, transfer saved two allocations and 8,225 requested bytes per scan. Median paired throughput increased 29% on Clang and 22.5% on GCC. The result retained all source bytes through caller replacement and sibling scanning. [Matched source-transfer comparison](byte_access/source_transfer.md). |
| Reading the next byte in an identifier | Production emits out-of-line byte-access calls. The combined checked-view prototype removes the call but retains an upper-bound test already established by the loop guard. | Acquire a stable pointer and length once. The split checked descriptor lets both compilers use the loop guard for the continuation load in cpp/php/js. | Native object inspection, optimized LLVM IR and GCC GIMPLE. The split prototype improved mixed throughput by 1.45–2.28× versus production. This measures the whole access change. |
| Entering the outer tokenizer loop | After the length comparison, Clang tests the signed cursor for negativity before the byte load. This scanner starts at zero and increments only below the signed length. | Providing this proven invariant at loop entry removes the sign branch. An equal-length NOP control isolates it at fixed code addresses. | Across cpp/php/js on pinned Clang, the fixed-layout control saved 0.208–0.215 ns/token on the operator corpus. A general lowering rule would need an equivalent proof. [Signed cursor comparison](byte_access/signed_cursor.md). |
| Appending each recognized token | Clang materializes a 24-byte argument on the stack and calls stock append once per token, including 2,560 times on this presized operator input. | A small capacity-available branch in the generated vector removes the hot call. Stack staging still survives there. Handwritten Clang stores the fields directly into the vector slot. | Median operator throughput gain was 8% on Clang and 1% on GCC across flavors. Aggregate spelling alone retains the stock Clang call. The vector generator owns the append path. [Native append comparison](byte_access/append.md). |
| Constructing the token in the reserved slot | The by-value fast path on Clang writes the fields to stack and reloads the record before storing it in the vector. | Pass offset, length and kind separately and construct in place after checking capacity. All three Clang objects store registers directly to the slot. Growth retains the existing fallback. | With split view and last-use move, median operator throughput relative to by-value fast append was 1.89× on Clang and 1.00× on GCC. Allocation traces matched. [In-slot experiment](byte_access/slot.md). |
| Reserving token storage | The generated vector allocates a 24-byte storage object in addition to its backing buffer. The handwritten vector needs just the backing allocation on this fixture. | An embedded native vector descriptor demonstrates a one-allocation representation. Changing the runtime representation requires a separate trade-off assessment, including empty-vector cost. | Measured allocation difference. No isolated execution-time attribution. Runtime representation owns this decision. |

With source transfer, split checked reads, in-slot append and last-use vector move together, the pinned operator-throughput gap to handwritten C++ was 24.2–25.9% on Clang and 7.2–16.2% on GCC across flavors. These are direct paired measurements of the whole scanner. A subsequent pinned Clang experiment substituted the handwritten recognizer while keeping scpp output storage and ownership. It saved 0.38–0.43 ns/token, closing 64–66% of the paired elapsed-time gap on this corpus. Recognition also differed under a common checksum sink. When replaying predecoded tokens, scpp in-slot storage took 0.14–0.16 ns/token less than std::vector. The remaining end-to-end difference is unassigned. [Recognition and storage controls](byte_access/recognition.md). [Matched handwritten comparison](byte_access/source_transfer.md#direct-comparison-with-handwritten-c)

With the proven nonnegative cursor included, the directly measured Clang throughput gap on the pinned operator corpus was 17.1%–19.3% across flavors, equivalent to 0.40–0.45 extra ns/token. [Paired cursor-to-handwritten comparison](byte_access/signed_cursor.md#direct-comparison-with-handwritten-c)

On the proven-cursor Clang scanner, table-based byte classification changed operator throughput by −2.0% to +2.2%, while improving mixed throughput by 15.8–19.1% and identifier throughput by 35.2–36.2%. Eager two-byte equals lookahead reduced operator throughput by 23.1–23.6% with the original classification. Keep the existing short-circuit lookahead for this workload. The table is a separate scanner-level candidate for identifier-heavy workloads. [Crossed classification and lookahead experiment](byte_access/classification.md).

A whole-file Clang comparison retained the original equals lookahead and added identical benchmark-only lexical coverage to both variants. The table improved the three billing batches by 11.1–13.6%. Four other sources gained 2.9–12.9%. The two remaining JS sources were effectively tied (median +0.5% and +0.6%, with zero inside both middle-50% ranges). All token streams matched the production PHP tokenizer. [File-level results and corpus](byte_access/source_classification.md).

Against the handwritten scalar-classification baseline on the same nine full source files, summing median scan times for one pass per file gives a 1.5% throughput gap on Clang and 0.8% on GCC. Individual files ranged from a 10.2% advantage to a 14.0% deficit for the table scanner across both compilers. [Pinned whole-file native comparison](byte_access/source_native.md).

For future findings, record the surviving native call, copy, allocation, load, store or branch, how often it runs, the condition that makes it redundant, and the inspection or timing that supports the claim. A source temporary alone is insufficient evidence.

Using uint32 for token offset and length is a deferred storage-layout option. Its input-size limit and overflow behavior would need a decision before adoption.
