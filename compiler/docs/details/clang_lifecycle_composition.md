# Clang assistance and lifecycle composition
Doc Status: supporting

Status: ownership decision and integration investigation, 2026-09-19. The [project objective](../README.md#project-objective)
explicitly permits Clang/LLVM/runtime dependencies. No new compiler phase, native
source-type export or lifecycle capability is implemented by this note.

The [lifecycle contract investigation](lifecycle_contracts.md) now records the
event inventory, field composition evidence and upstream discrepancies. It informs
the agreed boundary below. Earlier proofs remain feasibility evidence, not an
alternative current ownership rule.

## Ownership decision

- **Runtime origin:** native runtime types and implementations are prepared through
  Clang, exporting metadata and LLVM implementations.
- **Source origin:** our compiler owns complete source-type operations: field
  initialization, copying/assignment, destruction, custom bodies and their analysis.
  It selects imported operations for runtime fields and compiler-owned operations
  for source fields. Each operation has one implementation owner.
- **Mixed types:** `vector<MyStruct>` uses the runtime's vector implementation and
  our compiler's element operations through an explicit bridge. The same principle
  applies to ownership-wrapper combinations when they enter scope.
- **Clang assistance:** layout/ABI measurement and native declarations/adaptations
  remain allowed. They must reflect the compiler's accepted source contracts, not
  silently implement source field lifecycle again.

The earlier whole-structure proof delegated field composition to Clang and called
LLVM only for custom bodies. It proved bidirectional linkage, but did not prove
the selected complete-operation boundary. The subsequent investigation tests how
native templates invoke compiler-owned element operations without duplicate
native member construction/destruction. Production representation remains open;
this decision does not authorize a compiler-wide refactor or new source features.

The [complete source-operation adapter investigation](source_operation_adapter_proof.md)
now proves the selected division with a real runtime vector: native special members
forward to compiler-owned LLVM operations, including field composition. A separate
payload bridge handles LLVM-owned source storage without casting it to a native
adapter reference. This is an isolated representation candidate; its project import
and adaptation contracts are now defined in the
[source/native design contract](source_native_contract.md). Production integration
and the concrete coordinated migration remain unimplemented.

## Agreed direction

- Target a useful direct LLVM path at `-O0` and `-O1`, relying on LLVM optimization.
  S2S can serve broader compilation needs; independence is not a requirement.
- STAN (static analysis) is a first-class compiler objective. Keep source types,
  permissions, lifetime facts and diagnostic provenance available even when native
  operations are generated by Clang.
- Follow Simple C++ semantic contracts. Determine unclear construction, copying,
  assignment and destruction behavior from generated C++ and actual runtime types.
  Record deliberately added source capabilities as extensions.
- Reuse actual runtime operations through prepared metadata and ABI bindings where
  appropriate. LTO may optimize those calls; correctness must also hold without it.
  The present terminate-on-exception bridges do not imply S2S unwinding equivalence.

### Type ownership and imported combinations

The agreed working direction is that our compiler handles basic types and
source-defined structures/classes; imported types use prepared metadata and ABI
operations. Treat `shared_p<T>`, `unique_p<T>`, `weak_p<T>` and `value_p<T>` as
candidate imported families, subject to feasibility and execution-performance
proof. Each retains its own ownership, copying, borrowing and storage contracts.
In particular, imported `value_p<T>` retains inline storage.

An imported family containing a source type, such as `vector<MyStruct>` or
`shared_p<MyClass>`, requires both sides to participate. Our compiler owns the
source type's meaning and checked uses; preparation supplies the native family's
implementation. How native code obtains the faithful source definition and its
required operations needs an explicit adaptation contract. This direction does
not authorize all families now; source lifecycle remains compiler-owned.

The user requested a [focused execution-performance proof](performance_watchlist.md#focused-execution-performance-proof-for-imported-combinations)
for this boundary. Existing LTO feasibility evidence is not performance-parity
evidence for these combinations.

The [isolated source-record/vector proof](source_specialization_proof.md) now
establishes the bounded native/LLVM connection and reuse behavior. The user accepted
its measured 20–31% O1 small-vector lifecycle overhead for the fast development
compiler. That measurement is no longer an integration blocker; it does not settle
smart-pointer families or nontrivial source lifecycle behavior.

The subsequent [whole-structure lifecycle proof](lifecycle_preparation_proof.md)
passes automatic field composition and custom LLVM body callbacks, including one
body replacement that reuses prepared shell bitcode. It uses native declarations
and LLVM fixtures, not source compiler integration. The remaining boundary is a
project module with explicitly checked application imports; ordinary runtime
packages must retain their self-contained-link guarantee.

## Earlier implementation comparison

### Compiler-composed operations — selected ownership

The compiler derives an operation for a source structure from its ordered field
contracts. For a managed field, it calls the prepared runtime operation; for a
nested structure, it uses that structure's operation. One accepted operation plan
per concrete type/role can be reused at all source sites. Construction, assignment
and destruction retain their distinct preconditions and effects.

This avoids exporting every source type to C++ for ordinary field composition.
It does require the compiler to implement and validate composition rules, including
capability propagation, ordering and eventually partial-construction cleanup.
Existing field information helps, but does not by itself implement those rules.

### Clang-prepared operations for source types — feasibility evidence only

The compiler exports a faithful C++ declaration for a demanded source type and its
required dependencies. Clang prepares selected lifecycle operations and native
specializations; the compiler imports measured facts and callable implementations
through owned contracts. For the eligible generated C++ declarations, this can
reuse C++'s implicit special-member behavior.

The additional work is an exact source-to-C++ type mapping, declaration dependencies,
consistent native type identity/layout, capability import, diagnostic mapping and
artifact invalidation. A lookalike declaration with matching size is insufficient.
Source-defined methods or lifecycle bodies need an explicit linkage boundary;
they do not appear in Clang merely because fields were exported. The isolated
proof now demonstrates calls from a native lifecycle shell into LLVM bodies.
The [production boundary design](source_native_contract.md) specifies declaration
identity, layout, capabilities and project imports; its implementation remains pending.

Nested value types require complete field definitions in dependency order. Reuse
each demanded concrete definition instead of generating it per occurrence. Invalid
by-value cycles need source diagnostics. Pointer/reference dependencies have
different completeness requirements. Nesting alone should not cause combination
enumeration; concrete template demands and their dependencies determine the work.

## Why native preparation still participates

A native family such as `vector<MySourceStruct>` or `shared_p<MySourceStruct>`
requires a concrete native element representation and its demanded operations.
Field composition inside the compiler does not automatically make that source
type usable by a C++ template. Native preparation can compile a declared adaptation
that forwards source operations to their compiler-owned implementations.

An alternative runtime interface with explicit element operations is possible in
principle, but is a separate runtime design, with its own compatibility and cost.
The tested concrete adapter preserves exact type-specific operations and measured
storage; it is not a general claim that size/pointer information makes arbitrary
source types transparently compatible with native templates.

## Artifact and processing boundaries

Keep runtime-version/target/configuration artifacts reusable across projects.
Native artifacts involving application-defined types are project-specific and need
their own exact identities, dependency selection and retained outputs. Do not
regenerate or mutate the shared runtime package for each source file.

If chosen, a Clang preparation stage consumes fixed selected requests and produces
private results accepted by a join. It runs after its source contracts are known
and before consumers needing its capabilities/layout/ABI. Exact interleaving with
concrete preparation remains to be designed; this note does not prescribe an
unconditional late backend step. Type changes invalidate dependent native artifacts;
unrelated body edits should reuse them when their actual inputs are unchanged.

## Evaluation before integration

Retain the selected ownership and evaluate the native adaptation/import contract.
The isolated proofs cover field composition and a real vector specialization;
source-to-preparation export and compiler consumption are still pending. Determine
source eligibility from the selected contracts; the illustrative mention of
strings or smart pointers does not enable them as fields.

Assess total code/model complexity, initialization/copy/assignment/cleanup behavior,
source diagnostic quality, cold preparation cost and reuse after one body edit or
one type change. In a Clang-assisted proof, validate exact storage and operation
contracts against the generated declarations. Keep compiler-worker work partitioned
and avoid one Clang process per field, use site or source file.

The proofs establish bounded interoperability, not arbitrary source-type/native
template compatibility. Assess the complete system against the explicit adapter
requirements and remaining representation limits. Production integration remains
pending discussion; ownership has been decided.
