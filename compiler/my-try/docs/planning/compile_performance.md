## Findings and evidence

Small generated programs repeatedly process a large runtime header graph. The nullable
Elvis example took 7.71 s in the 12-worker fixture run, versus 1.93 s with PCH;
isolated timings were 3.03 s and 0.88 s. A separate Clang trace attributed 3.117 s
to the frontend and 0.049 s to the backend. Its preprocessed input was 3,424,631 bytes.
All 99 nullable fixtures passed both ways. Suite wall time fell from 47.63 s to
16.92 s, excluding 2.81 s for PCH creation. This is evidence of repeated header cost,
not a guarantee that all applications have the same bottleneck.

The follow-up synthetic generated-style C++ benchmark used integer arithmetic,
nullable/conditional lambdas and string truthiness. Each source had exactly the
stated number of lines, without blank/comment padding. It was generated by Python,
not by translating a real application through our frontend.

Ubuntu Clang 18.1.3, `-std=c++20 -Werror=return-type`, repository runtime includes,
no optimization/debug flags. Three serial compile-and-link runs per mode, alternating
mode order; PCH creation measured separately once per size. All 18 executables passed
independent Python checksum checks. Runtime header hashes matched throughout. Other

## PCH constraints and proposed cache boundary

A PCH serializes parsed compiler state, not a reusable application object file.
Clang still processes application code, required instantiations, code generation and
linking. Lazy declaration loading does not imply partial invalidation or repair.

Clang supports a chain such as `runtime.pch -> project.pch -> feature.pch`.
A child is built against its parent, and loading the child loads the chain. Separate
project children can serve separate C++ output units; arbitrary independent PCHs
cannot be combined into one translation unit. Clang modules offer a composable graph
and are a candidate to evaluate, not an adopted requirement.

A changed input header requires rebuilding its PCH artifact, not patching individual
declarations inside it. Changes propagate to dependent child PCHs and consuming
objects. A project-only change can preserve the runtime parent. Keep stable runtime
material in the base; consider project declarations/type definitions separately from
frequently changing ordinary function bodies. Header-defined templates may need bodies.

The native build/cache layer should own persistent artifacts and invalidation. Match
compiler/toolchain identity, target/ABI, language/build flags, macros, include search
configuration and transitive input dependencies, including system headers. Use content
fingerprints with a sound change-detection policy; do not assume runtime stability or
rely solely on mtime/size. Preserve Clang's own validation. Its input checks normally
use metadata; `-fpch-validate-input-files-content` can compare contents after an mtime
change, not unconditionally hash every input on every use. Explicit stale PCH use
normally fails; the build layer schedules regeneration.

Build one artifact per compatible cache entry, coordinate concurrent creators, publish
only completed artifacts atomically, and retain retry obligations after failure.
Application body edits must not invalidate a runtime-only PCH. The test runners'
current per-run PCH is not a persistent cache and does not prove these requirements.

## Required work after the operational milestone

- [ ] Establish representative application and edit/rebuild benchmarks; separate
  source preparation/emission, C++ header processing, instantiation, IR generation,
  optimization, machine-code generation and linking where tooling permits.
- [ ] Address [precise runtime include selection](incremental_strategy.md#debt-precise-runtime-includes-for-faster-c-compilation).
  C++ emission maps prepared requirements to narrow runtime-owned public surfaces;
  it must not duplicate semantic decisions or runtime checks.
- [ ] Evaluate persistent runtime PCH reuse and runtime/project chains or a few stable
  profiles. Compare a small core plus ordinary specialized includes against broader
  bundles. Avoid a cache entry for every incidental feature combination by default.
- [ ] Integrate with retained C++ fragments and future stable output units/object reuse.
  Current assembly is one `main.cpp`; PCH does not avoid recompiling unchanged
  application bodies inside that unit. Keep semantic and native-build dependency graphs
  distinct. Measure fan-out from signature/layout and runtime-header changes.
- [ ] Investigate the LLVM/IR route described below; record evidence and a decision.
- [ ] Deliver measured improvements and focused correctness/invalidation proofs, or
  explicit blockers with bounded follow-up work and user review. A discussion alone
  or an unmeasured backend preference does not close this mandatory task.

## Required LLVM/IR investigation

Examine both Clang-generated LLVM and the future direct LLVM generation perspective.
Clang can emit textual IR using `-S -emit-llvm`, or bitcode using `-c -emit-llvm`.
Use those boundaries to measure frontend versus downstream cost and investigate
reusing unchanged IR/bitcode units, runtime artifacts and object files. Compare total
cold and incremental latency against C++ + PCH + object reuse, with matched target,
optimization/debug settings and equivalent behavior. Measure optimization and linking
costs rather than assuming LLVM intermediates make the whole pipeline faster.

Emitting IR from C++ still requires Clang's C++ frontend on a cache miss. Bitcode is
not a substitute for all header parsing or template instantiation, and PCH is not IR.
Review runtime ABI, data layout, exceptions, ownership/lifetime, template-generated
code and toolchain compatibility before treating runtime IR as reusable across units.
Direct LLVM generation could bypass C++ parsing for application code, but requires a
sound lowering/runtime boundary and its own maintenance/correctness evidence.

This future investigation does not resume the parked LLVM backend now. Any direct
backend work must first adapt it to the shared semantic preparation model; do not
create a second semantic compiler or infer language meaning from Clang's emitted IR.
Agree cross-owner changes before implementation, including runtime or output redesign.

## Acceptance evidence

Cover no-op rebuilds; body-only edits; signature/layout edits; added/removed runtime
requirements; project/runtime/system-header changes; compiler/flag/macro changes;
missing/stale artifacts; concurrent builders; failed creation and retry. Verify that
unchanged outputs preserve bytes/timestamps and only required consumers rebuild.
Keep `--no-pch` correctness checks to expose missing includes and visibility changes.
Use representative checked failures and lazy branches, not just successful checksums.
Report cold setup separately from reuse, serial latency separately from parallel
throughput, plus artifact size/memory and realistic application scaling. LLVM candidates
need equivalent behavior and diagnostics where required; faster compilation alone is
not acceptance. Do not claim a native compiler rebuild from generated-program tests.
