# Chapter 08: multi-file C++ and incremental native builds
Doc Status: planning

Recorded: 2026-10-06. Baseline: `480b2543` on `v0.2/develop`.
Status: entry selection, partitioned cross-file generation and bounded bare-record
declaration-versus-definition dependencies and persistent publication implemented.
Bounded native caching and the core edit/rebuild acceptance matrix are implemented.
Validation-overhead optimization is deferred to CH15-NATIVE-CACHE-PERF-01.
This is not a language spec.

## Direction and evidence

Preserve the output architecture adopted in the
[next-generator handoff](../../../../specs/planning/s2s_next_generator_technical_handoff.md):
individual type headers, narrow callable declarations, stable implementation groups,
precise dependencies and content-aware publication. The
[original latency findings](../../../../specs/planning/s2s_compile_latency_findings_2026_09_19.md)
explain the motivation. Historical timings are evidence, not promises for this compiler.
The [performance task](compile_performance.md) remains open; this roadmap brings its
runtime-PCH boundary into the initial build architecture, not the later LLVM investigation.

Source organization and native compilation organization are separate. Initially an
implementation group may follow a source file; neither that mapping nor one C++ file
per function is a permanent requirement. No combined all-project declaration header
or application PCH should become a dependency of every unit.

The [2026-10-16 lowering/toolchain plan](clang_units_and_mold.md#immediate-architecture-explicit-implementation-group-assembly)
narrows the next structural work to explicit implementation-group assembly with
existing membership and paths preserved. Automatic unit splitting and multi-file
classes are CH15 debt, not prerequisites for Ninja/Clang/Mold integration.

## Current owners and limits

- Input discovery already owns modules and module-relative source identities.
- Collection/preparation already handles multiple sources and resolved cross-file calls.
- C++ retains declaration/body fragments and publishes callable/type headers, initial
  per-source implementation groups and one `entry.cpp` through the common artifact API.
- `06_native/Native_Runner` currently executes LLVM output. It is not a C++ project
  builder. C++ fixture helpers have per-run PCH support, not a persistent build cache.
- `06_native/Native_CPP_Build` owns the bounded persistent C++ object/link/runtime-PCH
  cache. Its acceptance evidence and remaining limits are recorded below.

Reuse these semantic records and fragment owners; do not introduce another symbol or
type model. Existing semantic invalidation is not the native recompilation graph.

| Owner | Responsibility |
| --- | --- |
| Inputs / shared semantic model | Source and symbol identity, selected entry, checked types, bindings and semantic dependencies |
| Preparation | Language validation and settled facts; no header paths, grouping or PCH decisions |
| C++ backend | Artifact identity, C++ names, declaration/completeness requirements, grouping and generated bytes |
| Coordinator / publication | Sequence stages, publish a consistent output revision, acknowledge consumed changes after success |
| Native build | Objects, link membership, toolchain configuration, depfiles and persistent PCH/cache lifecycle |

Workers do not invoke later stages. Shared records carry facts, not processing hooks.

## Entry and identity contract

One selected source supplies executable statements; other sources supply declarations.
Discovery/directory order must never select execution order. Follow the build-owned
composition contract in [project_build_v1](../../../../specs/project_build_v1.md).
The implemented convenience is to infer the sole source for existing
single-source invocations; multiple sources require explicit selection. Validate
non-entry executable statements instead of silently ignoring them. The authoritative
v0.2 entry rule is in `specs/project_build_v1.md`, linked above.

Backend artifact keys use stable logical module/source identity, canonical symbol
identity and artifact role. They must not use process-local object IDs, traversal
counters, source line numbers or absolute checkout paths. Module reconciliation keys
may remain paths; separate logical names now select output identity. A single unnamed
module uses `main`; multi-module programs require explicit names.

Keep semantic identity distinct from C++ spelling and filesystem-safe encoding.
Namespace support must extend qualified identity, not replace every identity with
an unrelated scheme. Duplicate symbols remain errors, not artifact-key merging.

## Artifact and dependency contract

The backend plan associates each artifact with its identity, role, semantic owners,
relative output path, final content fingerprint and dependencies. The manifest also
maps implementation units to link members. Lowering/build-context fingerprints
invalidate incompatible reuse without renaming every logical artifact.

Dependencies distinguish callable/type declaration, complete type, inline/template
definition and runtime interface, with a reason. Derive these from settled facts
and actual lowering requirements, never lexical name scanning. Build dependencies
also include native compiler-discovered transitive headers.

Each definition has one owner and each object one link membership. Default arguments
belong to declarations; templates/inline definitions remain available where required.
Existing record, container, reference and ownership behavior must remain unchanged.

Prepare the complete artifact set before publication. Unchanged final bytes preserve
their files. A consistent manifest/publication boundary must prevent the build from
observing a partially updated revision; do not assume multiple file renames are one
atomic operation. Delete only obsolete files owned by the previous manifest.
On failure retain retry obligations and do not acknowledge unconsumed preparation
changes. A previous successful executable is not a successful build of a failed revision.

## PCH from the beginning

Use one stable runtime-only PCH per compatible native build configuration initially.
Do not put frequently changing project declarations or bodies into it. More profiles,
chains or modules require measured benefit and a separate decision.

The native build layer owns compatibility keys covering toolchain, target/ABI,
language/options/macros, include search configuration and transitive inputs, including
system headers. Keep native compiler validation enabled. Application body edits must
not invalidate the runtime PCH; runtime input changes must invalidate consumers.
Coordinate concurrent creators, publish completed cache entries atomically and retry
failed creation without accepting partial artifacts. Depfiles and content-aware
validation must account for changes across compiler process restarts.

## Edit/rebuild acceptance matrix

| Change | Expected native effect |
| --- | --- |
| No change | No generated rewrites, object compilation or relink |
| Ordinary non-inline function body | Owning implementation group and link; no caller rebuild or runtime PCH rebuild |
| Unrelated new function | New/changed owning group and link; existing unrelated declaration artifacts unchanged |
| Signature/default change | Changed declaration and affected implementation/consumers; no unrelated units |
| Record layout | Complete-definition consumers and affected definitions; not unrelated declarations |
| Delete source/function | Remove obsolete owned artifacts and link members; reject remaining invalid callers |
| Runtime header / compiler / flags | Invalidate affected PCH/objects using the build compatibility contract |
| Failed generation/build, retry, concurrent creation | No partial successful revision or poisoned cache; successful recovery |

Also check output identity after restart and checkout relocation, missing cached files,
and a representative no-PCH build. Report cold PCH creation separately from warm reuse.
Do not promise comment-only no-ops when observable diagnostic data changes.

## Migration gate and non-goals

Recommended coordinated migration: single-source and multi-source compilation use
the same artifact-producing backend. Update the current C++ output API, CLI delivery
and fixture/native consumers together; do not keep a second monolithic renderer.
This crosses backend, coordinator and tooling ownership. The user approved this
coordinated migration on 2026-10-06. The benefit is one generation contract; the risk is disrupting
existing output consumers, requiring focused single-source and multi-source proofs.
The artifact-delivery checkpoint preceded the now-completed partitioning cutover.

Reconcile stale imported Chapter 08 cards with current normative specs before their
slices: old `require_once` textual lowering is not project composition, and the old
type-blind generator restriction does not apply to shared semantic preparation.
Namespace import cards also contain historical supported/rejected discrepancies.

Not included now: class/method features lacking their later chapter model, new source
include semantics, package ABI/export redesign, LLVM work, project-wide PCH, automatic
profile tuning or general build-system replacement. Reuse existing build facilities
where they meet this contract; the roadmap does not authorize changing legacy S2S.

## Bounded type-dependency precision — 2026-10-06

Slice 3 distinguishes declaration-only bare-record uses from complete-definition
uses inside the C++ backend. Callable headers forward-declare bare records, including
by-value prototype parameters/results. Implementation signatures require definitions
for values, not references. Reference call temporaries, forwarding and aliases preserve
name-only requirements; value materialization/replacement, embedded fields and member
access explicitly record layouts. Inferred `auto` copies cannot lose their dependencies.
Signature fragments retain separate prototype includes and definition-only includes;
complete requirements dominate forward declarations within each artifact.

This extends the existing type representation/fragment path. Parsing, collection,
semantic facts and preparation scheduling do not learn C++ headers. No second symbol
model, lexical dependency scanner, extra AST walk or project umbrella header is added.
Compared with the old generator's spelling-based forward-name scan, settled canonical
types decide which source definition is being named here.

Boundary: runtime template/modifier headers and their source payload definitions remain
conservatively included, even at declaration sites. A future per-binding incomplete-type
contract needs actual runtime/template proofs, not an assumption based on pointer-like
storage. Broader inline/template declaration roles follow their future language model.
This is bounded native dependency precision, not minimized semantic invalidation or
proof of incremental object/PCH reuse.

Evidence (local temporary paths):

- `/tmp/my-try-ch08-type-dependencies-20261006-3/summary.json`: five PHP suites,
  26 separate-unit executions with/without PCH, 30 standalone-header checks without
  PCH, and three clang transitive-dependency checks. Covers layout-only edits,
  clean/incremental equality, name-only forwarding, inferred copies, whole-record
  replacement, nested fields and conservative template payload dependencies.
- `/tmp/my-try-ch08-type-functions-20261006-1/summary.json`: 12 PHP suites and
  77 function executions without PCH passed. The first dependency-run attempt had a
  Python bytes/text assertion mismatch after successful C++ checks; the harness was
  corrected without changing language behavior. Runners used documented CLI fallback.

The implementation follows the portable-PHP authoring constraints; enum requirements
use explicit typed entrypoints rather than introducing enum-valued parameter defaults.
The compiler itself was not rebuilt natively in this slice.

## Content-aware disk publication — 2026-10-06

Slice 4 adds optional coordinator-owned `Output_Publication` and CLI `--output`.
One immutable artifact API serves memory-only and disk consumers. The
[publication protocol](../architecture/output_publication.md) owns the manifest,
stable lock, atomic pending recovery inventory, ready marker and reader obligations.
Preparation changes are acknowledged only after successful disk publication.
Unchanged artifacts/manifest preserve inode/mtime; edited/unowned files are refused,
missing owned output restored, and obsolete owned artifacts retired.

User-approved cross-owner expansion: shared portable output read/write/remove/root
and SHA-256 primitives, with PHP/native implementations and PHS error bridges.
Mechanism stays in the shared adapter; policy stays in the coordinator. The
[adapter contract](../../../../specs/portability/output_files.md) is bounded to trusted
Linux output trees and cooperative locking, not hostile-filesystem or power-loss
protection. A recovery journal is embedded in the atomic status file, avoiding a
failure gap between two metadata-file replacements.
